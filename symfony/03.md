# Symfony Bundles Internals and Large-System Structure

Bundles are Symfony's packaging boundary: code, config, routes, services, templates, translations, and compiler passes can all live inside one unit.

## 1) Why Bundles Matter

In large systems (Pimcore, Akeneo-style apps), bundles give you modular ownership:
- each domain has its own extension point
- core and custom code stay isolated
- upgrades are safer because overrides are explicit

## 2) Core Internals

A bundle is usually a class extending `Symfony\Component\HttpKernel\Bundle\Bundle`.

```php
final class CatalogBundle extends Bundle
{
}
```

Key bundle hooks:
- `build(ContainerBuilder $container)`: register compiler passes
- `getPath()`: bundle root path
- extension class (`DependencyInjection/*Extension.php`): load services/config

## 3) Boot Sequence

At kernel boot:
1. `Kernel::registerBundles()` returns bundle list.
2. Symfony initializes bundle instances.
3. Container compilation loads each bundle extension.
4. Compiler passes run and finalize service graph.

That means bundle order and extension loading impact final behavior.

## 4) Practical Pattern for Large Systems

Use domain bundles:
- `ProductBundle`
- `PricingBundle`
- `ImportExportBundle`

Inside each bundle keep:
- `Controller/`
- `Application/` (use-cases)
- `Domain/` (business rules)
- `Infrastructure/` (Doctrine, API clients)
- `Resources/config/services.yaml`

## 5) Common Mistakes

- Putting all logic in `App\` only.
- Sharing mutable services across unrelated modules.
- Overusing global parameters instead of bundle-local config.

## 6) Best Practices

- Keep bundle public API small (interfaces/events).
- Use service tags for extension.
- Add compiler passes only when needed; keep them deterministic.

## 7) Quick Recap

Bundles are module boundaries plus integration hooks. If you structure by domain bundles, scaling teams and features becomes far easier.
